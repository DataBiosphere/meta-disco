Meta-disco Use case 1 — detailed 23 August 2026

Three Views of One Genome

Two hundred and twenty-four people in AnVIL have their genome represented three ways at once. Most of what you would do with that has already been published — which makes it the right first test of a search AnVIL cannot currently perform, because the answer is known in advance.

01

The cohort

Intersecting sample identifiers across three open-access AnVIL datasets gives 224 participants who simultaneously have a de novo diploid assembly, short reads aligned to CHM13, and short reads aligned to GRCh38 — plus deposited variant calls against both references.

The cohort has a useful split built into it. Of the 224 assemblies, 121 are trio-phased (named pat/mat, phased using parental reads) and 103 are phased without a trio (hap1/hap2). That is a free methodological control, and a confounder to watch — see the variations.

Reference assignments are not assumed. They come from meta-disco's own content-based classification of the 2026-08-02 run:

The last row is the point. A de novo assembly correctly resolves to not_applicable for reference assembly, because it has no reference. That is what makes it usable as truth.

02

The search that finds it

Stated plainly, the query is:

participants WHERE
    exists( data_type = assembly,        reference_assembly = not_applicable )
AND exists( data_type = aligned_reads,   reference_assembly = CHM13 )
AND exists( data_type = aligned_reads,   reference_assembly = GRCh38 )

Three predicates, all over metadata we already produce, joined on a participant. No phenotype, no ancestry, no consent logic. It is the simplest possible participant-level query — and it cannot be expressed in AnVIL today, because the files index carries no participant key and the donor identifiers are minted per snapshot.

What makes it answerable right now is that the participant is recoverable from the file name, at a measured one-to-one purity. So the cohort below is real and buildable this week; the metadata work is what makes it repeatable and makes the next query cheap.

03

The analysis

The template is assembly-truth benchmarking: use each person's own assembly to grade their own short-read variant calls, then ask how that grade changes with the reference you aligned against.

The move that makes it work is turning an assembly into a truth set. Align the two haplotype contigs back to a reference, read off the differences, and you have a per-individual variant call set plus an explicit statement of where you are confident — derived from long reads, independent of the short-read pipeline being tested.

01

Assemble the cohort

Run the query above. Materialise a table of 224 participants with the DRS or signed URL for each artefact.

  • Azul manifest
  • Terra data table
→ cohort table, 224 rows
02

Turn each assembly into a truth set

Align both haplotype FASTAs to the chosen reference and call the differences. The output is a diploid VCF plus a confident-region BED — the regions where both haplotypes aligned cleanly enough to trust a call, and, just as importantly, where they did not.

Run this twice per person: once against GRCh38, once against CHM13. That second run is the whole reason the comparison is interesting.

  • dipcall
  • minimap2
→ 448 truth VCFs + confident BEDs
03

Grade the short-read calls against it

Compare the deposited short-read VCF to the matching assembly-derived truth VCF, restricted to the confident regions. Small variants and structural variants need different comparison logic — a 300 bp insertion represented three different ways is the same event, and only SV-aware comparison will say so.

  • hap.py / rtg vcfeval
  • truvari
→ recall + precision per person per reference
04

Stratify by how hard the region is

A single genome-wide recall number hides the entire result. Short reads are near-perfect in unique sequence and fail in specific, nameable places: segmental duplications, tandem repeats and VNTRs, the MHC, immunoglobulin and KIR loci, and the challenging medically relevant genes. Break every metric down by region class.

On CHM13 add one stratum that has no GRCh38 counterpart at all: the newly resolved sequence — centromeric satellite, acrocentric short arms, previously collapsed duplications. There is no established truth set there. Assemblies are the only route in.

  • GIAB stratification BEDs
  • CMRG
  • CHM13-only regions
→ the actual result table
05

Difference the references

For each person and each region class, subtract the GRCh38 result from the CHM13 result. Positive means CHM13 recovered calls that GRCh38 lost; negative means the migration cost you something. Aggregate across the cohort, then split by whatever subject axis you chose.

→ Δrecall, Δprecision per stratum, per group

The assemblies are five percent of the bytes. If you accept the deposited variant calls rather than re-calling from reads, you never touch a CRAM, and the whole analysis runs on assemblies plus VCFs — about 13 GB per person.

That gives a natural two-stage plan. A pilot of three to five people is a laptop-scale job: download roughly 40–65 GB, run dipcall and a comparison, and see a result the same day. The full 224 belongs on Terra, co-located with the buckets, where the CRAMs stay put and only summary tables come back. Only re-call from reads if the question is specifically about the caller rather than the reference.

Compute is dominated by step 2, twice per person. Treat the per-sample cost as a pilot measurement rather than a quoted figure — the honest answer is that it is small enough not to be the constraint, and egress and storage will dominate the bill before CPU does.

The trap in the deposited calls

Step 3 as written — compare the deposited CHM13 calls against the deposited GRCh38 calls — does not measure the reference. Reading 203,719 cached VCF headers shows the two call sets come from different pipelines:

Call setCallerModeFilteringFreeze
1000G_high_coverage GATK 3.5 joint · GenotypeGVCFs VQSR CCDG_13607 · 2019-02-19
ANVIL_T2T · T2T_CHRY GATK 4.x per-sample gVCF largely none Cromwell/Terra · 2020–21

Marker counts across the scanned headers: 75,246 GATK-4-style HaplotypeCaller invocations in ANVIL_T2T and 90,378 in T2T_CHRY, essentially all in gVCF mode with almost no recalibration; against 3,252 GATK-3-style invocations with VQSR in the 1000G deposit. A CHM13-minus-GRCh38 delta computed across those would substantially measure GATK 3 versus GATK 4 and VQSR versus none.

Worse for a metadata system: the reference itself is under-specified. Six distinct reference files appear across these three datasets, and they collapse into two enum values.

ANVIL_T2T and ANVIL_T2T_CHRY are sibling workspaces from one consortium, and they use different CHM13 versions — v1.0 with a grafted GRCh38 chrY in one, v2.0 in the other. Both classify as CHM13. Aligning to them is not the same experiment.

How to address it

Use the GRCh38 arm inside the T2T workspaces, not the 1000G deposit. The T2T workspaces carry their own GRCh38 calls — 1,056 headers naming GRCh38_full_analysis_set_plus_decoy_hla.fa, drawn from a later CCDG freeze (CCDG_14151 · 2020-08-05) than the 1000G deposit. That is closer to the published comparison. It is not a clean matched control either — its provenance still differs from the CHM13 arm — so read the paper's methods before relying on it.

Or re-call uniformly. Both CRAM sets are present. One caller, one version, one filter regime, both references. Roughly 10 TB of reads and the only route to a defensible reference delta — and the prerequisite for any of the browser tracks below the coverage one.

Or do not difference at all. Grade each call set against assembly truth independently and report per-pipeline, never subtracting. Cheap, honest, and still yields the assembly-truth coverage track, which depends on no caller at all.

And regardless: record the provenance. Caller, version, filtering and the specific reference file are all sitting in headers this project already fetches, caches and parses — and all are discarded. Capturing them is what would let the query itself demand a pipeline match instead of leaving the user to discover this the hard way.

04

What has already been done with exactly this data

This has to come before any claim of value, because the answer is: most of it. The ANVIL_T2T workspace is not raw material awaiting analysis — it is the deposited output of a published study, and its own description says so.

“…all 3,202 short-read samples from the recently extended 1000 Genomes
Project collection that we analyze using the GATK HaplotypeCaller for
SNVs and indels on the NHGRI AnVIL Cloud Platform.”
                          — ANVIL_T2T workspace description

That is Aganezov et al., Science 2022 (PMID 35357935), “A complete reference genome improves analysis of human genetic variation” — the T2T companion paper. The workspace links to it directly. Their reported findings map onto most of what this use case was framed as producing:

Published finding (Aganezov 2022)Overlaps which part of this use case
Adds >80 Mbp of sequence usable for variant callingthe CHM13-only stratum
Eliminates false positives in MAP2K3, ZNF717“pick your hard region”
Corrects missed variants from false duplications (CBS, KCNE1)“pick your hard region”
Improves insertion/deletion balance for SVsthe variant-class axis
Reduces false de novo mutations and Mendelian violations in triosthe trio-consistency variation, entirely

Two further pieces of prior art matter. Donor-specific assembly benchmarking is an established method, not an idea — McGee et al. (bioRxiv 2026, PMID 42395516) use exactly this framing to separate platform-intrinsic sequencing error from reference bias. Their scope is two samples and the question is sequencer chemistry, not reference choice. And HPRC Release 2 has a paper (PMID 42539208, bioRxiv 2026): 460 haplotypes — matching the 460 assembly FASTAs in AnVIL_HPRC_R2 exactly — including, notably, continuous local-ancestry estimates across every genome.

So what is actually left

A timing gap, and it is real but narrow. Aganezov's truth set was 17 long-read samples plus GIAB. HPRC2's 230 diploid assemblies did not exist in 2022. Applying donor-specific assembly truth to the reference question, at n=224 rather than n=17, is an increment that post-dates the published work — but it is an increment, not a new question.

I have not read the HPRC2 full text. Its abstract closes on “a host of new tools and applications,” which could easily include this. Anyone taking this forward should read that paper before claiming the gap is open.

05

Why run it anyway

Because the point of this use case was never the biology.

UC 1 exists to demonstrate that a participant-level query across datasets is possible and worth building. For that job, an analysis whose answer is already published is not a weakness — it is the ideal choice. It is a validation harness with a known-good result.

If the search finds 224 people, the pipeline runs, and the output reproduces the MAP2K3 and ZNF717 false-positive elimination and the CBS/KCNE1 recovery that Aganezov reported, then every link in the chain is proven: the participant crosswalk is correct, the reference classification is correct, the cross-dataset join is correct, and the data is what the metadata says it is. A novel result could not prove any of that, because there would be nothing to check it against.

That reframes the deliverable honestly. This is a capability demonstration with an independent oracle, and the science claim shrinks to a modest, defensible one: extending assembly-based truth from a handful of samples to a couple of hundred, on a question the field has already shown is worth asking.

The claim to make

Not a new finding. A reproducible one, found by a query nobody can currently run.

Aganezov's team assembled this cohort by hand, inside the consortium that generated it. The test of participant-level search is whether an outsider can reconstitute the same cohort in an afternoon — and then vary it.

06

Variations on the same template

The pipeline stays fixed. Each user changes one axis and gets a different paper. This is what makes it a template rather than a study — and the axes marked in red are the ones that need metadata AnVIL does not currently expose.

Axis — reference

GRCh38 versus CHM13

The default framing. Every one of the 224 has both alignments already deposited, so this variation costs nothing extra to set up.

available now · 224 people
Axis — region class

Pick your hard region

Restrict to the MHC, or KIR, or immunoglobulin loci, or CYP2D6, or SMN1/SMN2. Clinically consequential, notoriously unreliable, and each is a self-contained result.

available now · public BEDs
Axis — variant class

SNV, indel, or structural

The reference effect is expected to be largest for SVs and repeat-length variation, and smallest for SNVs in unique sequence. Confirming or refuting that gradient is itself the finding.

available now
Axis — assembly method

Trio-phased versus not

121 of the cohort are phased with parental reads, 103 without. Does truth quality track phasing method? A methodological control — and a confounder to rule out before trusting any population comparison.

available now · 121 / 103
Axis — assembly version

HPRC release 1 versus 2

44 people have assemblies in both releases. Re-running on each shows how much a truth set moves when the assembly improves — the stability question that every benchmark ought to answer about itself.

available now · 44 people
Axis — ancestry

Population and superpopulation

The variation with the most at stake: does reference choice help or hurt differently by ancestry? The HPRC2 paper ships continuous local-ancestry estimates for every genome, which is a finer instrument than population labels and was not available to the 2022 work.

1000G panel or HPRC2 local ancestry — use case 2
Axis — family

Trio consistency

Mendelian violation rate is a second, orthogonal truth signal that needs no assembly. Aganezov already reported CHM13 reducing false de novo calls, so this axis is a reproduction target rather than an open question — which is exactly what makes it a good validation check.

needs pedigree — use case 2 · published result to match
Axis — caller

Deposited calls versus your own

Re-call from the CRAMs with a different caller and grade both against the same truth. This is the one variation that requires touching the 10 TB of reads.

available now · CRAM-scale
Why this shape of cohort matters

The redundancy is the asset.

Three representations of one genome look like duplication in a file browser. Viewed per participant they are a controlled experiment that already exists, fully funded and fully public, waiting for a query that can see across datasets.

07

What is verified, and what is not

Prior art established on 2026-08-23 from the ANVIL_T2T workspace description (Azul) and PubMed: Aganezov 2022 (PMID 35357935), McGee 2026 (PMID 42395516), HPRC2 (PMID 42539208). Abstracts and the workspace description were read; none of the three full texts were.

Measured directly from the 2026-07-29 corpus snapshot and meta-disco's 2026-08-02 classification run: the cohort size of 224, the 121/103 phasing split, the 44 people in both HPRC releases, every file count and byte total, and the reference assignments in the table above.

Assumed, and worth checking before committing

Cohort size is a floor. 224 comes from an anvil14 snapshot. ANVIL_HPRC has not yet been reindexed into anvil15, so this cannot currently be re-derived live. Only 45 of the 259 release-1 samples have assembly FASTAs in AnVIL against 230 of 231 in release 2 — worth confirming that release 1 assemblies are genuinely absent rather than named in a form the scan missed.

Assembly completeness is unexamined. The presence of two FASTAs per person says nothing about contiguity or how much of each haplotype is actually assembled. Truth-set quality depends on it, and it should be measured per sample rather than assumed uniform.

The deposited VCFs are no longer taken at face value — checked 2026-08-23 across 203,719 cached VCF headers, and they are not pipeline-comparable. See “the trap in the deposited calls” above. What remains unverified is how Aganezov handled this; only the abstract and the workspace description were read, not the methods.

Tooling is named, not validated. dipcall, hap.py, rtg vcfeval and truvari are the standard choices for these steps, but no workflow has been sourced or run here. Treat step 2 onward as a design, not a tested pipeline.
